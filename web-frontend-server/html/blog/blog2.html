One Network, Eleven Containers: Docker Compose, API Gateway, and Load Balancing

Nguyễn Trần Hoàng Nhân – 523H0164

Why Use a Dedicated Network?

All minicloud containers join the cloud-net bridge network (10.10.10.0/24). Docker provides internal DNS on this user-defined network, allowing containers to connect by name, such as http://application-backend-server:8081. Static container IP addresses also allow BIND9 records to point to the intended services.

docker-compose.yml: Defining the System

A single file defines 11 containers, their ports, volumes, and startup dependencies. Three configuration choices matter:

  • restart: unless-stopped allows containers to restart after the Docker daemon restarts, unless they were explicitly stopped.
  • Each service has a healthcheck. The gateway uses depends_on with condition: service_healthy to wait for the Web and App services to become ready.
  • Image tags are declared in Compose and the Dockerfiles. Some use release versions; the locally built Web and App images use a configurable tag that defaults to latest. Tags such as stable-alpine may change over time.

API Gateway: A Shared Entry Point

The gateway runs Nginx on port 80 and forwards requests according to their paths:

PathDestination
/the two web servers
/api/Flask (removing the /api prefix)
/auth/Keycloak
/student/Flask at /student

Round Robin Load Balancing

The web-frontend-server1 and web-frontend-server2 containers run the same image. The gateway groups them in an upstream block; Nginx uses Round Robin by default to distribute requests between them.

upstream web_backend {
    server web-frontend-server1:80;
    server web-frontend-server2:80;
}

Each web server exposes its hostname in the X-Served-By header and the page footer. Refresh the page several times to observe both hostnames. If one server becomes unavailable, the gateway can retry eligible requests against the other server.
