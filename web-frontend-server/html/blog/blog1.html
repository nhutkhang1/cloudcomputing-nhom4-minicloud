From Static Pages to an Authenticated API: Web, App, Database, and Keycloak

Nguyễn Nhựt Khang – 523H0145

Web Frontend: Serving Static Files with Nginx

This page is packaged in the minicloud-web image, built from nginx:stable-alpine. The Dockerfile replaces the default configuration, copies conf.default and the html/ directory, and adds the Nginx Prometheus Exporter. The location ^~ /blog/ block uses alias to serve the blog directory.

Application Backend: Flask

The backend is a Flask application listening on port 8081 inside the container, published on host port 8085. It provides four main endpoints:

  • /hello returns a JSON greeting for a basic availability check.
  • /student reads the student list from students.json.
  • /students-db reads the students table in MariaDB.
  • /secure returns data only when the request includes a valid token issued by Keycloak.

Database: Initializing Data with MariaDB

MariaDB runs the .sql files in /docker-entrypoint-initdb.d during initialization when its data directory is empty. The project uses 001_init.sql to create the minicloud database and 002_studentdb.sql to create studentdb. Flask connects with a dedicated account granted read access to studentdb instead of using root.

Keycloak: Who Can Access /secure?

Keycloak issues tokens using OpenID Connect. The project defines the realm_523H0145 realm, two users, sv01 and sv02, and the public client flask-app. Flask retrieves the realm's public keys (JWKS) and checks the RS256 signature, expiration, issuing realm, and myapp audience.

curl -s -X POST http://localhost:8081/auth/realms/realm_523H0145/protocol/openid-connect/token \
  -d grant_type=password -d client_id=flask-app \
  -d username=sv01 -d password=...

Key Takeaway

Tokens connect the authentication flow: Keycloak signs them, the client sends them, and Flask validates them. Flask does not need the user's password or a call to Keycloak for every request; it caches the public keys.
